## 排查 ruizhi（codex 定制版）"error decoding response body" 报错

用户配置（`~/.ruizhi/config.toml`）：`model = "gpt-5.5"`, `model_provider = "ruijie-uniapi"`, `base_url = "https://gptauth.ruijie.com.cn/v1"`, `wire_api = "responses"`, `requires_openai_auth = true`。

**根本原因**：`codex-rs/login/src/auth/manager.rs:189` 的 `REFRESH_TOKEN_URL` 硬编码为 `http://gptauth.ruijie.com.cn/oauth/token`（HTTP 而非 HTTPS）。第 190 行 `REVOKE_TOKEN_URL` 同样是 HTTP。

**完整错误链**：
1. access token 过期 → codex 用 refresh_token 刷新
2. POST 发到 `http://.../oauth/token` → 服务器返回 301 重定向到 HTTPS（响应体是 HTML）
3. reqwest 跟随 301，POST → GET（301 标准行为）
4. GET `https://.../oauth/token` → 返回 200 + HTML 页面（不是 JSON）
5. `.json::<RefreshResponse>()` 尝试把 HTML 当 JSON 解码 → 失败 → "error decoding response body"
6. token 刷新失败 → turn 请求也失败（同样的错误消息传播）

**验证**：curl 测试确认 HTTP 端点返回 301 HTML，HTTPS 端点返回正常 JSON。

**修复方案**：把 manager.rs:189-190 的 `http://` 改为 `https://`。待用户确认后执行。

## Responses→Chat 自动 fallback 可行性分析

用户问：能否在遇到 "stream disconnected before completion: stream closed before response.completed" 时自动切到 Chat 协议。

**当前机制**：
- `CodexErr::Stream(..)` 是可重试错误（`protocol/src/error.rs:200`，`is_retryable()==true`）
- 重试循环在 `core/src/session/turn.rs:1143-1206`，最多 `stream_max_retries()` 次
- 重试时用**相同 wire_api**（`client.stream()` 每次调 `wire_api_for_model()`，结果不变）
- 已有 fallback：WebSocket→HTTP（`responses_retry.rs:31-46`，`try_switch_fallback_transport`），但**无 Responses→Chat**

**关键文件**：
- `core/src/responses_retry.rs:22` — `handle_retryable_response_stream_error`，重试/fallback 决策点
- `core/src/client.rs:1916-1921` — `stream()` 中 wire_api 选择
- `core/src/session/turn.rs:2033` — 产生 `CodexErr::Stream("stream closed before response.completed")`
- `model-provider-info/src/lib.rs:170` — `wire_api_for_model()`

**实现方案**：在 `handle_retryable_response_stream_error` 加 Responses→Chat fallback 分支（类似现有 WS→HTTP），需在 `ModelClientSession` 加 `wire_api_override`。codex 已有完整 `stream_chat_completions_api` 实现。待用户确认是否实现。

## 已实现：Responses→Chat 自动 fallback

最终实现只对网关明确拒绝 Responses API 的错误切 Chat。普通 `stream closed before response.completed` 仍保留原有 Responses 重试语义，避免把短暂网络断流误判为模型不支持 Responses。

**改动文件**：

1. `core/src/client.rs`：
   - `ModelClientSession` 加 `wire_api_override: Option<WireApi>` 字段
   - `new_session()` 初始化 `None`
   - `stream()` 优先使用 override（`self.wire_api_override.unwrap_or_else(|| wire_api_for_model(...))`）
   - 新增 `try_switch_to_chat_api(&mut self) -> bool`：设置 override=Chat，清 websocket session，返回是否首次切换

2. `core/src/responses_retry.rs`：
   - 新增 `should_fallback_to_chat(err: &CodexErr) -> bool`：检测 `InvalidRequest(body)` / `UnexpectedStatus(body)` 含 "does not allow Responses API" 或 `"code":"400005"`
   - 8 个单元测试全部通过

3. `core/src/session/turn.rs`：
   - 重试循环中 `is_retryable()` 检查前插入 `should_fallback_to_chat` 检测
   - 命中且首次切换 → 发 Warning 事件、retries=0、continue（用 Chat 重试）
   - 已切换过 → 走正常重试/错误路径

**400005 错误传播路径**：网关 HTTP 400 → `TransportError::Http` → `map_api_error` → `CodexErr::InvalidRequest(body)`（`is_retryable()==false`，原行为直接报错）。新逻辑在 is_retryable 检查前拦截。

**验证**：
- `just fmt` 通过
- `just test -p codex-core responses_retry stream_no_completed::retries_on_early_close`：9 个测试通过
- 完整 `just test -p codex-core` 在本机有既有/环境失败（缺 `test_stdio_server`、code-mode host、web_search 工具列表等），其中本改动曾触发的 stream 早关断预期已通过收窄 fallback 判定解决。
